# 인사이트 설계: 가설과 검증 방법

## Context
- 데이터 수집 계획은 혼합안으로 확정했다. 구성은 다음과 같다.
  - A: SEC 분기 재무
  - B: pypistats 일별 다운로드
  - C: BigQuery 최적화 실험 (2단계)
  - 합성 고객 코호트 (선택)
- 이번 단계에서는 수집된 데이터로 무엇을 증명하거나 반증할지 정한다. 코드는 작성하지도 실행하지도 않는다.
- 원칙 3가지
  1. 가설마다 채택·기각 기준을 **데이터를 보기 전에** 적는다. 결과를 보고 기준을 바꾸는 체리피킹을 막기 위해서다.
  2. 데이터로 증명하지 못하는 것은 대시보드에서 주장하지 않는다.
  3. 대시보드 첫 화면은 "가설 판정표"로 한다. 새 데이터가 들어오면 판정이 자동으로 갱신된다.

근거 표기: **[확인]** 앞선 대화에서 직접 호출해 확인한 값 / **[지식]** 2026-05 기준 지식 / **[미확인]** 착수 전에 확인이 필요한 항목

## 원문 주장 중 검증 가능한 범위

원문의 논리 사슬: 소비 기반 과금 → 성장은 기존 고객 확장에서 → 확장은 새 워크로드로 → 새 워크로드는 데이터 도메인 인력이 만든다

| 연결 고리 | 공개 데이터로 검증 | 가설 |
|---|---|---|
| 성장은 기존 고객 확장에서 나온다 | 가능 | H1 |
| 약정보다 실제 소비가 매출을 결정한다 | 가능 | H2 |
| 확장은 새 워크로드(Python·ML·AI)로 일어난다 | 간접 가능 (개발자 생태계 범위 한정) | H3 |
| 플랫폼 사이에 워크로드가 이동한다 | 간접 가능 | H4 |
| 설계가 소비(비용)를 좌우한다 | 직접 실험 | H5 |
| 데이터 도메인 인력이 소비를 만든다 | **불가능** | 해석으로만 서술 |

## 가설

### H1. 성장 동력: "매출 성장의 과반은 기존 고객 확장에서 나오지만, 그 비중은 줄고 있다"
- 계산 (2020년 이후 분기별)
  - 기존 고객 기여분 ≈ (NRR − 1) × 전년 TTM 제품매출
  - 기여 비중 = 기여분 ÷ (당기 TTM 제품매출 − 전년 TTM 제품매출)
  - TTM은 최근 12개월 합계를 뜻한다.
- 보조 지표: $1M 초과 고객 수 증가율(+27% [확인])과 전체 고객 수 증가율을 비교한다. 대형 고객이 더 빨리 늘면 확장형 성장으로 본다.
- 판정 기준
  - 전반부 지지: 모든 분기에서 기여 비중 > 50%
  - 후반부 지지: 최근 8분기 비중 추세의 기울기 < 0
- 함정
  - Snowflake의 NRR은 2년 창과 코호트 기준으로 정의되어 위 근사식과 다르다. 근사식은 기존 고객 기여를 약간 과대평가할 수 있으므로, 구현할 때 10-K의 정의 원문을 확인한다.
  - 제품매출은 XBRL에 없어서 텍스트 파싱이 필요하다 [확인].
- 데이터: 1단계 첫 실행에서 바로 가능하다. IPO 이후 이력이 공시에 있다.

### H2. 약정 vs 소비: 두 경쟁 가설 중 어느 쪽인가
- (a) 건전 신호: 고객이 약정을 빨리 소진하고 조기에 갱신한다. 소진 속도가 오른 뒤 1~4분기 안에 RPO가 증가한다.
- (b) 경고 신호: 약정 규모가 줄거나 계약 기간이 짧아진다. RPO 커버리지가 계속 하락한다.
- 지표
  - 소진 속도 = 분기 매출 ÷ 기초 RPO
  - RPO 커버리지 = RPO ÷ (분기 매출 × 4), 즉 이미 확보한 매출이 몇 년치인가
- 이미 계산한 값: 커버리지는 2025-07에 1.51년, 2026-07에 1.45년이다 (RPO $6.9B → $9.0B, 분기 매출 $1.145B → $1.547B) [확인]
- 검증 방법: 4분기에 대형 계약이 몰리는 계절성을 없애기 위해 전년 동기 대비로 비교하고, 시차는 0~4분기를 본다.
- 판정 기준
  - (b): 커버리지가 전년 대비 4분기 연속 하락하고, RPO 성장률 < 매출 성장률
  - (a): 소진 속도가 상승한 뒤 RPO 성장률이 반등
  - 둘 다 아니면 판단 보류
- 함정: 표본이 약 22분기뿐이라 상관계수나 p값 대신 방향이 일치하는지로 판정한다.

### H3. 워크로드 다변화: "Snowflake 위 사용이 SQL 조회에서 Python·ML로 넓어지고 있다"
- 원문의 "AI가 데이터 플랫폼 소비를 증폭한다"는 주장에 가장 가까운 공개 신호다.
- 지표: (snowflake-snowpark-python + snowflake-ml-python) ÷ snowflake-connector-python 다운로드 비율, 90일 이동평균
- 판정 기준: 비율이 2분기 연속 상승하면 지지
- 함정
  - ml 패키지가 snowpark를 의존성으로 함께 설치시킨다. 그래서 절대값을 합산하지 말고 비율의 추세만 본다.
  - 결론은 "개발자 생태계" 범위로 한정한다. 매출과 연결한 해석은 P를 통과한 뒤에만 한다.
- 데이터: 첫 실행에서 180일치로 초기 판독이 가능하고, 이후 누적할수록 확실해진다.

### H4. 경쟁 구도: "변환 파이프라인(dbt)의 무게중심이 Snowflake에서 Databricks로 이동 중이다"
- 지표: dbt-snowflake / dbt-databricks / dbt-bigquery의 점유율(세 패키지 합 대비), 90일 이동평균
- 노이즈 줄이기: pypistats의 OS별 분할을 쓴다. Windows+macOS는 사람 개발자, Linux는 서버·CI로 보고, 사람 신호만으로도 같은 결론이 나오는지 확인한다.
- 판정 기준: 사람 신호와 전체 신호 모두에서 점유율이 2분기 연속 같은 방향으로 움직이면 지지
- 함정: dbt Fusion 엔진은 PyPI 밖에서 배포된다 [지식]. 플랫폼별 전환 속도가 다르면 점유율이 왜곡될 수 있으니 결론에 명시한다.

### H5. 비용 설계 (2단계, C): "같은 결과를 내는 쿼리도 설계에 따라 과금 바이트가 10배 이상 차이 난다"
- 대조 실험 (단계마다 하나씩 개선)
  - V0: 전체 `SELECT *`
  - V1: 필요한 컬럼만 선택
  - V2: V1 + 파티션 필터
  - V3: V2 + 클러스터링된 사본 테이블
  - V4: 사전 집계 테이블
- 측정: `JOBS_BY_PROJECT`에서 `total_bytes_billed`와 `total_slot_ms`를 뽑는다. 매일 반복해서 분산까지 기록한다.
- 통제
  - 모든 버전의 결과가 같은지 행 수와 해시로 확인한다.
  - 쿼리 캐시를 끈다. 끄지 않으면 0바이트로 측정된다.
  - V0는 dry run 추정치만 쓴다. 무료 1TB 한도를 지키기 위해서다.
- 판정 기준: V0 대비 V4 절감률 ≥ 90%이면 지지
- 함정: 샌드박스 테이블은 60일 뒤 만료되고, V3·V4용 테이블을 샌드박스에서 만들 수 있는지는 [미확인]이다.
- SA/CE 업무와의 연결: 실제 고객 대화에서 다루는 소재다.

### P. 전제 검증: "다운로드 증가율은 매출 증가율과 같은 방향으로 움직인다"
- 목적: B를 매출 선행지표로 써도 되는지 판정한다. 통과하지 못하면 B는 "생태계 관심도" 패널로만 쓴다.
- 방법: snowflake-connector-python 월별 다운로드의 전년 대비 증가율과 분기 제품매출의 전년 대비 증가율을 시차 0~4분기로 비교한다.
- 데이터 문제
  - pypistats의 180일치로는 불가능하다.
  - BigQuery 공개 PyPI 테이블에서 2020년 이후 월별 집계를 한 번 백필한다. dry run 추정치가 예산(예: 100GB) 이하일 때만 실행한다.
  - 예산을 넘으면 데이터가 2년 쌓이는 2028년으로 미룬다.
- 판정 기준: 증가율 방향 일치율 ≥ 70%이면 보조지표로 채택
- 함정: 두 시계열 모두 우상향이라 수준(level)끼리 비교하면 가짜 상관이 나온다. 반드시 증가율로 비교한다.

### (선택) 합성 코호트: 설명 모델이지 검증이 아니다
- 역산 질문: "NRR 126%를 만들려면 고객당 1년에 워크로드가 몇 개 늘어야 하나"
- 이탈률과 워크로드당 소비량 가정을 명시한다.
- 화면에 "시연용 가정"이라고 표시한다.

## 검증 불가 → 대시보드에서 주장하지 않을 것
- 데이터 도메인 인력이 소비를 늘린다: 인력 데이터와 고객 데이터가 없다. H1 결과에 기댄 "논증"으로만 서술한다.
- 다운로드 증가가 매출 증가를 일으킨다는 인과
- 최적화로 단가가 내려가면 장기적으로 소비가 늘어난다는 주장

## 우선순위와 판정 가능 시점
| 순서 | 가설 | 데이터 | 판정 가능 시점 |
|---|---|---|---|
| 1 | H1, H2 | A | 1단계 첫 실행 (과거 이력 있음) |
| 2 | H3, H4 | B | 첫 실행에서 초기 판독, 2분기 누적 후 확정 |
| 3 | P | A + B 백필 | 백필이 가능하면 즉시, 불가능하면 2028년 |
| 4 | H5 | C | 2단계 |
| 선택 | 합성 코호트 | — | 언제든 |

## 대시보드 반영
- 첫 화면은 가설 판정표로 한다. 가설마다 현재 판정(지지·기각·보류), 핵심 수치, 마지막 갱신일을 보여 준다.
- 가설별 상세 패널을 하나씩 둔다.
- 판정 기준은 설정 파일에 상수로 고정한다. 나중에 기준을 바꾸면 Git 이력에 남는다.
- 구현할 때 생길 예상 파일:
  - `analysis/hypotheses.py`: 가설별 판정 함수
  - `config/thresholds.yaml`: 사전 등록 기준값
  - `app/scorecard.py`: 판정표 화면

## 분석 검증 방법 (구현 후)
- NRR 파싱: 이미 확인한 값(2026-07 126%, 2026-01 125%) [확인]과 과거 3개 분기를 수동으로 대조한다.
- H1 상식 검사: 10-Q는 매출 증가를 "주로 기존 고객의 소비 증가" 덕분이라고 명시한다 [확인]. 계산한 비중이 50% 미만이면 계산식 오류로 본다.
- H2: 커버리지 1.51 → 1.45가 재현되는지 확인한다.
- H5: 캐시 적중 여부가 false이고, 모든 버전의 결과 해시가 같은지 확인한다.
- 전체: 파이프라인을 두 번 실행해도 판정이 같은지 확인한다(멱등성).
