# 계획 v2: 데이터 플랫폼 월 비용(TCO) 비교 대시보드 + 변동 자동 게시

## Context
- **방향 전환:** "가설 검증형 분석"에서 "계속 돌아가는 제품"으로 바꾼다. 제품의 흐름은 다음과 같다.
  - 가격 수집 → 같은 워크로드의 월 비용 추정 → 대시보드 → 변동 감지 → 글 생성 → 게시
- **사용자 결정 사항 (2026-09-11)**
  - 비교 대상: 같은 워크로드의 월 비용 추정(TCO)
  - 독자: 포트폴리오용 웹 아카이브
  - 게시 위치: 자체 웹 아카이브(GitHub Pages) + LinkedIn
  - 글 생성: 템플릿 문장
  - 게시 방식: 처음엔 사용자 승인, 안정되면 자동
- **기준:** 막힘(접근권한, 무료 데이터)을 최소화한다. 이전 합의(혼합안)에서 유지하는 원칙은 두 가지다.
  - 가입이 필요한 외부 서비스를 최소화한다.
  - 기간이 정해진 무료 체험은 계속 수집하는 용도로 쓰지 않는다.
- **이 문서의 의미:** 승인은 방향 확정이다. 구현은 사용자가 착수를 지시한 뒤 0단계부터 시작한다.

표기: **[확인]** 직접 호출해 확인 / **[지식]** 2026-05 기준 지식 / **[미확인]** 0단계에서 확인 / **[가정]** 모델 가정(대시보드에 공개)

## 1. 가설 재편 (v1 → v2)
고객이 내는 돈(TCO)과 벤더가 버는 돈(NRR)은 같은 돈의 양면이다. 메인은 고객 관점, 보조는 벤더 관점으로 둔다.

| v2 | 내용 | v1과의 관계 | 판정 방법 |
|---|---|---|---|
| **T1** 월 비용 순위는 워크로드 유형에 따라 뒤바뀐다 | 시나리오 W1~W3에서 1위 플랫폼이 서로 다른가 | 신규 | 모델 추정 결과. 성능 가정을 ±50% 흔들어도 순위가 유지되면 "견고", 뒤집히면 "가정에 민감"으로 표시 |
| **T2** 서울 리전 프리미엄은 서비스마다 다르다 | 서울/미국 단가 비율 (Redshift, Azure Databricks, VM, 스토리지) | 신규 | 공시 가격만으로 계산해서 성능 가정이 필요 없다 → 신뢰도 높음 |
| **T3** 플랫폼 선택보다 설계 개선이 월 비용에 더 큰 영향을 준다 | 설계 개선 절감률(실측) vs 플랫폼 간 비용 차(T1) | **v1 H5를 승격** | 절감률 > 플랫폼 간 차이면 지지. 실측은 BigQuery만 가능하므로 일반화 범위를 명시한다 |
| **H1·H2** 실적 코너 | 성장 동력(NRR), 약정 vs 소비(RPO 커버리지) | 유지 | v1 기준 그대로 적용. 실적 8-K 공시가 올라오면 갱신한다 |
| H3·H4 | PyPI 추세 | 보류 | 게시할 거리가 부족할 때 선택적으로 추가한다 |
| P, 합성 코호트 | — | 제외 | TCO 주제와 관계가 없다 |

- 대시보드에서 주장하지 않을 것: 플랫폼 간 비교를 "측정값"처럼 표현하지 않는다. T1은 항상 "가정 기반 추정"으로 표기한다.

## 2. TCO 모델
- **시나리오** (`data/manual/workloads.yaml`, 가정과 출처를 함께 적는다) [가정]
  - W1 소규모 BI: 평일 10시간, 소형 컴퓨트
  - W2 야간 배치 ETL: 매일 2시간, 중형 컴퓨트
  - W3 비정기 대용량 탐색: 월 N TiB 스캔
  - 공통: 저장 용량 10TB
- **계산식:** 월 비용 = 컴퓨트(단가 × 시간 또는 스캔량) + 스토리지. 네트워크 송출 비용은 제외하고, 제외했다는 사실을 명시한다.
- **플랫폼 간 환산:** Snowflake 웨어하우스 크기, Databricks SQL 크기, Redshift RPU, BigQuery 스캔량 사이의 대응표 [가정]
  - H5 실측(BigQuery 과금 바이트)으로 보정한다.
  - Snowflake 30일 트라이얼은 **1회성 보정 실험**에만 쓴다(선택).
- **리전:** 미국 동부와 서울을 비교한다 (AWS ap-northeast-2, Azure Korea Central, GCP asia-northeast3)

## 3. 가격 소스와 막힘 수준
| 플랫폼 | 수집 방법 | 막힘 |
|---|---|---|
| Redshift, EC2, 스토리지 | AWS 대량 가격 파일 (인증 불필요) [지식] | 낮음. 파일이 크니 서비스별 파일만 받는다 |
| Azure Databricks DBU, VM | Azure Retail Prices API (인증 불필요) [지식] | 낮음. SKU 이름은 [미확인] |
| BigQuery | 수동 가격표 + 가격 페이지 변경 감지. 2단계 이후 Cloud Billing Catalog API(키 필요)로 교체 가능 | 중간 |
| Snowflake 크레딧 | **수동 가격표** (`data/manual/snowflake_prices.csv`) + 가격 페이지·서비스 소비표 PDF 변경 감지 | 중간. 스크래핑하지 않는다. 약관과 robots.txt는 [미확인] |
| Databricks 직판(AWS) | 수동 가격표 + 변경 감지 | 중간 |
| 실적 (H1·H2) | SEC EDGAR submissions·companyfacts + 8-K 본문 [확인] | 낮음 |

- 페이지 변경 감지는 게시하지 않는다. 대신 GitHub Issue를 열어 "가격 페이지 변경, 확인 필요"를 알리고, 사용자가 수동 가격표를 고친다.

## 4. 변동 감지 → 글 → 승인 → 게시
- **이벤트 기준** (`config/thresholds.yaml`, 사전에 고정)
  - E1 가격 변동: 단가 차이가 생겨 어떤 시나리오의 월 비용이 ±1% 이상 바뀌거나 순위가 바뀐 경우
  - E2 실적 공시: 추적 기업의 새 8-K(item 2.02)가 올라온 경우
  - E3 실험 월간 요약: H5/T3를 매달 요약 (선택)
  - 같은 날 생긴 이벤트는 한 글로 합친다. 게시는 하루 최대 1건.
- **글 생성:** Jinja2 템플릿으로 만든다 (`templates/post_*.md.j2`).
  - 숫자는 계산 결과(`events.json`)에서만 끼워 넣는다.
  - 게시 전에 "글에 나온 모든 숫자가 `events.json`에 있는가"를 자동 검사하고, 틀리면 중단한다.
- **승인 흐름 (GitHub PR = 승인 버튼)**
  1. 매일 도는 수집 워크플로가 이벤트를 발견하면 초안을 `posts/`에 쓰고 PR을 연다. 이벤트가 없으면 데이터 스냅샷만 커밋한다.
  2. 사용자가 PR을 머지하면 승인이다.
  3. 머지(main에 push)가 게시 워크플로를 트리거한다: 사이트 빌드 → Pages 배포 → LinkedIn 게시(요약 + 아카이브 링크).
  - 함정: GITHUB_TOKEN으로 한 자동 머지는 다른 워크플로를 트리거하지 않는다 [지식]. 그래서 자동 게시로 전환할 때는 수집 워크플로 안에서 바로 게시하는 방식으로 바꾼다.
- **자동 전환 조건:** 연속 N건(예: 5건)을 수정 없이 승인하면 전환을 검토한다.
- **LinkedIn** [지식]
  - 개발자 앱에 LinkedIn 페이지를 연결해야 한다.
  - 필요한 권한: Share on LinkedIn(w_member_social) + OpenID(회원 ID)
  - 토큰은 60일마다 만료되고, 갱신 토큰이 없어서 주기적으로 직접 다시 로그인해야 한다.
  - 대응
    - 만료 7일 전에 워크플로가 Issue로 알린다.
    - 재인증은 로컬 스크립트 1개로 처리하고, 결과를 GitHub Secret에 갱신한다.
    - API 버전 헤더가 약 1년마다 종료되므로 연 1회 갱신 점검을 한다.

## 5. 저장소 구조와 배포
```
consumption-insights/
  collectors/   aws_prices.py, azure_prices.py, sec_filings.py, page_watch.py
  data/raw/     날짜별 CSV·Parquet 스냅샷 (DuckDB 파일은 커밋하지 않음)
  data/manual/  snowflake_prices.csv, bigquery_prices.csv, workloads.yaml
  model/        tco.py (시나리오 × 단가, 민감도)
  detect/       diff.py (이전 스냅샷과 비교 → events.json)
  publish/      render_site.py (Jinja2 → 정적 HTML, Plotly 차트), render_post.py, linkedin.py
  templates/    post_price_change.md.j2, post_earnings.md.j2
  config/       thresholds.yaml
  posts/        승인된 글 (아카이브 원본)
  docs/         00_hypotheses_v1.md (기존 문서 보존), 01_plan_v2.md
  .github/workflows/  collect.yml (매일, 정각 피함), publish.yml (main push 시)
```
- **공개 저장소가 필요하다.** GitHub Pages를 무료로 쓰려면 공개 저장소여야 한다 [지식]. 이전의 "비공개로 시작" 결정을 변경한다.
- 공개 저장소의 60일 무활동 규칙은 매일 스냅샷 커밋이 막아 줄 것으로 본다. 봇 커밋이 활동으로 인정되는지는 [미확인]이다.
- 대시보드는 정적 HTML + Plotly로 만든다. Streamlit은 쓰지 않는다. Pages 배포와 아카이브를 한 사이트로 합치기 위해서다.

## 6. 단계
| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0 점검 | 아래 [미확인] 항목을 각각 5분 안팎으로 테스트 | 막히는 항목마다 대체 경로를 정함 |
| 1 | AWS·Azure·수동 가격표 수집 → TCO 계산(T1·T2) → 정적 대시보드 Pages 배포 | 시나리오 3개 × 플랫폼 4개 × 리전 2개 표와 차트가 보임 |
| 2 | 변동 감지 → 템플릿 글 → PR 승인 → 아카이브 게시 | 가짜 가격 변동을 주입하면 PR이 생기고, 머지하면 게시됨 |
| 3 | LinkedIn 연동 + 토큰 만료 알림 | 사용자가 확인한 뒤 첫 테스트 게시 1건 |
| 4 | 실적 코너(H1·H2, SEC) + H5 BigQuery 실험 → T3 판정 | 8-K 이벤트로 글 초안 생성, T3 판정 표시 |
| 5 | 안정화 후 자동 게시로 전환 | 연속 N건 무수정 승인 |

**0단계 점검 목록**
- GitHub Actions 서버에서 SEC, AWS 가격 파일, Azure API를 호출할 수 있는지
- Azure Retail API에 Azure Databricks(서버리스 SQL) SKU가 있는지
- AWS Redshift 가격 파일의 크기와 서울 리전 포함 여부
- Snowflake·Databricks 가격 페이지의 약관과 robots.txt (변경 감지 허용 여부)
- LinkedIn 앱 생성 조건 (페이지 연결 필요 여부), 토큰 만료 정책
- 공개 저장소 60일 규칙과 봇 커밋의 관계
- (4단계 전) BigQuery 샌드박스에서 `JOBS_BY_PROJECT` 조회와 CTAS 가능 여부

## 7. 검증 방법
- 가격 수집: 수집한 값 3개를 공식 가격 페이지와 수동으로 대조한다.
- TCO: W1 한 시나리오를 스프레드시트로 손계산해서 모델 결과와 일치하는지 확인한다.
- 민감도: 성능 가정을 ±50% 바꿨을 때 T1 라벨(견고/민감)이 바뀌는지 확인한다.
- 변동 감지: 스냅샷 사본에 가짜 가격 변동을 주입하면 이벤트와 PR이 생기고, 변동이 없으면 PR이 없는지(멱등성) 확인한다.
- 글 숫자 검사: 글의 숫자 하나를 바꿔 넣으면 검사가 실패하는지 확인한다.
- 게시: `--dry-run` 모드는 외부 게시만 빼고 전 과정을 실행한다. LinkedIn 실제 게시는 매번 사용자 확인 뒤에 한다.
- 실적: 2026-07 분기의 NRR 126%, RPO $9.0B [확인]이 재현되는지 확인한다.
