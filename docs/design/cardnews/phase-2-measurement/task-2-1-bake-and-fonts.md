## 세부 계획

**목표:** HTML을 설치된 브라우저로 구워 1080×1350 PNG와 PDF를 만드는 방식이 실제로 되는지, 디자인 요소가 제대로 그려지는지 코드를 많이 쓰기 전에 확인한다.

**확인하려 한 것**
1. 로컬(Windows, Edge 또는 Chrome)에서 구워지는가
2. CI(ubuntu-latest)에서 구워지는가
3. **한글이 네모(두부)로 나오지 않는가** — 양쪽 모두
4. 그라데이션·라운드·CSS 막대가 제대로 그려지는가

**시험 카드:** 한글 초대형 제목, 그라데이션 단어, 회색 본문, 라운드 카드, CSS 막대 4개, 상·하단 바. 외부 요청 0건, 시스템 글꼴 목록.

**판정 방식:** PNG 크기는 헤더에서 직접 읽고, PDF 쪽수는 바이트에서 센다. **한글 표시와 그라데이션은 사람이 눈으로 본다**(두부 글자도 픽셀은 그려지므로 자동 판정하지 않는다).

**실패 시:** 멈추고 보고한 뒤 Playwright 안을 다시 묻는다.

## 결과

### 로컬 [확인]

| 항목 | 결과 |
|---|---|
| 브라우저 | Edge. Chrome은 설치돼 있지 않다 |
| PNG / PDF | 1080×1350 / 카드 한 장이 PDF 한 쪽 |
| 한글 | 정상. 맑은 고딕으로 그려진다 |
| 그라데이션·라운드·CSS 막대 | 정상 |

### CI [확인] (실행 34697297970)

| 항목 | 결과 |
|---|---|
| 브라우저 | Google Chrome 152와 Chromium이 미리 설치돼 있다 |
| **한글 글꼴** | **0개**(`fc-list :lang=ko`) |
| 글꼴 설치 전 굽기 | **성공하지만 모든 한글이 두부 글자** |
| `fonts-noto-cjk` 설치 후 | 한글 정상 |

**결론:** 카드를 굽는 워크플로에는 `fonts-noto-cjk` 설치가 필수다. 없으면 실패하지 않고 두부 글자 카드가 조용히 만들어진다. 디자인 관점에서 가장 위험한 발견이다.

### 디자인에 넘긴 실측

| 실측 | 반영 |
|---|---|
| 104px 제목은 한 줄에 약 10자가 들어가고 그 이상은 넘친다(본문 폭 968px의 약 93%) | 스크립트 4절 글자 수 상한표: 표지 10자×2줄, 본문 제목 14자×2줄, 리드 30자×3줄, 항목 32자×2줄, 각주 40자×2줄 |
| 로컬(맑은 고딕)과 CI(Noto Sans CJK)의 줄바꿈 지점이 다르다. 같은 문장이 로컬 `비교되지 않습니 / 다`, CI `비교되지 않습니다. 같 / 은`으로 끊겼다 | 글자 수 상한을 넉넉하게 잡는다. 이후 한 음절 줄 문제(2-3)와 글꼴 정합(5-2)으로 이어진다 |
| 내용이 적은 장은 아래 여백이 크다 | 본문 블록 세로 위치 조정(3-2) |

### 결함 수정 (2026-09-14)

2-2 시험 굽기 중 파일이 생기지 않는다는 실패가 났다. **Edge가 종료 코드 0을 먼저 돌려주고 실제 파일은 분리된 하위 프로세스가 몇 초 뒤에 쓴다** [확인]. 파일 크기가 두 번 연속 같아질 때까지(최대 60초) 기다린 뒤 임시 프로필을 지우도록 고쳤다. 디자인과 무관하지만, 이후 모든 실물 굽기가 이 수정에 기댄다.

## 계획과 달라진 점

- PDF 쪽수를 셀 때 `/Type /Pages` 노드까지 세어 5쪽을 6쪽으로 잘못 읽었다. 정규식을 `/Type\s*/Page(?![s])`로 고쳤다.
- 실제로 구운 PNG 크기를 확인하는 테스트를 더해 테스트를 2개가 아니라 3개로 만들었다.

## 남긴 것

- 굽기는 **임시 프로필**로만 한다. 사용자 브라우저 프로필과 로그인 세션을 건드리지 않는다.
- 로컬과 CI는 서로 다른 글꼴로 그린다는 사실. Phase 4·5에서 이 차이를 줄였다.
