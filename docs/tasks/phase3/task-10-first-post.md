## 게시 전 결함 수정: PDF 강조 문구 테두리선 (2026-09-15)

### 발견

사용자가 `cards.pdf`를 열었더니 그라데이션 강조 문구(`월 사용료 추적`, `승인`, `대시보드`, `비교되지 않습니다`)마다 **문구를 감싸는 상자 가장자리에 희미한 주황 실선**이 보였다. PNG에는 없다. PDF 안에서 스크롤하면 사라졌다 다시 나타난다.

### 원인 [확인]

- 강조 문구는 `background: linear-gradient(...)` + `background-clip: text` + `color: transparent`로 그린다(그라데이션 사각형을 글자 모양으로 오려 낸다).
- **PNG**는 브라우저가 픽셀로 바로 그리므로 문제가 없다.
- **PDF**로 저장하면 Chromium이 이 기법을 문구마다 "그라데이션 사각형 + 소프트 마스크 두 겹"으로 기록한다. PDF 내부 확인 결과:
  - 사각형이 강조 상자 전체를 채운다(예: 표지 `48 573 615 138 re f`).
  - 첫 번째 마스크는 상자 사각형을 반전한 것(`/TR {1 exch sub}`)이다.
  - 두 번째 마스크는 글자 모양이다.
  - 소개 카드 PDF에 `/SMask`가 11개 있다.
- 보기 프로그램이 첫 마스크의 가장자리를 부드럽게(안티에일리어싱) 그리면서 반전 값이 0이 되지 않는다. 그 결과 사각형 테두리가 한 픽셀 폭으로 비친다.
- 배율과 화면 조각에 따라 가장자리가 걸리는 픽셀이 달라서 나타났다 사라진다.

### 재현 [확인]

사용자의 보기 프로그램과 다른 렌더러(pdf.js 3.11.174, 헤드리스 Edge)로 표지 강조 상자 오른쪽 가장자리 열을 쟀다. 상자 높이 전체에서 배경 대비 색 편차의 평균을 비교했다.

| 배율 | 현재 PDF | 승인된 PNG 5장으로 조립한 시험 PDF |
|---|---|---|
| 1.37배 | 2.0 | 0.0 |
| 2.13배 | 1.7 | 0.0 |
| 3배 | 13.2 | 0.0 |

3배 확대 이미지에서 현재 PDF는 강조 문구를 감싸는 선이 보이고, 시험 PDF는 선이 없다. 시험 PDF는 5쪽, 273,919바이트, `/SMask` 0개, 이미지 5개다. 쪽 전체가 여백 없이 카드로 채워진다.

LinkedIn은 올린 PDF를 자체 변환기로 그려서 보여 준다. 그 변환기에서 선이 보이는지는 확인할 방법이 없다 [미확인]. 서로 다른 렌더러 두 곳에서 재현됐으므로 게시 전에 고친다.

### 결정 D23 (2026-09-15 사용자 승인, A안)

**카드 PDF는 굽기가 끝난 PNG를 한 쪽에 한 장씩 실어 만든다.** 카드 HTML을 PDF로 직접 인쇄하지 않는다.

| 안 | 내용 | 채택 |
|---|---|---|
| **A** | 승인 대상 PNG로 PDF 조립 | **채택.** PDF와 PNG의 모습이 같아지고, 원인(소프트 마스크)이 사라진다. CI에서 굽는 정기 카드도 같은 함수를 쓰므로 함께 해결된다 |
| B | 강조 문구를 단색으로 | 기각. 승인한 디자인이 바뀐다 |
| C | 강조 문구를 SVG 글자로 | 기각. 템플릿과 레이아웃 검사를 크게 고쳐야 한다 |

**대가**
- PDF 안의 글자를 선택하거나 검색할 수 없다. LinkedIn 문서 게시와는 관계없다.
- 크게 확대하면 선명도가 PNG 해상도(1080×1350)에서 멈춘다.

### 세부 계획

**목표:** `bake()`가 만드는 `cards.pdf`에 소프트 마스크가 없고, 쪽마다 그 장의 PNG가 여백 없이 실린다. 소개 카드를 다시 굽고 게시 주소에 반영한다.

| 파일 | 변경 |
|---|---|
| `publish/render_cards.py` | `pdf_pages_html(pngs)` 추가(쪽마다 PNG 한 장, `@page` 1080×1350px, 여백 0). `bake()`는 PNG를 모두 구운 뒤 이 HTML을 임시 폴더에 써서 `browser.print_pdf`로 굽는다. 쪽수 검사에 더해 **이미지 수 = 장수**, **`/SMask` 없음**을 검사하고 어긋나면 `ValueError` |
| `tests/test_render_cards.py` | 아래 테스트 |
| `data/cards/intro/cards.pdf` | 다시 굽는다. PNG·`cards.html`·`linkedin.md`는 바뀌지 않아야 한다 |
| 문서 | 이 파일(결과), `CLAUDE.md`(D23, 확인된 사실, 진행 로그), `docs/phases/phase-3-linkedin.md`, `docs/plans/phase3-linkedin-cardnews.md`(D23), `docs/plans/phase3-card-design.md`(PDF 산출 방식), `docs/design/cardnews/`(새 단계 문서와 README) |

**테스트 (130 → 132)**

| # | 테스트 | 확인 내용 |
|---|---|---|
| 1 | `test_pdf_pages_show_each_png_on_its_own_full_page` (신규, 브라우저 불필요) | PNG마다 `<img>` 하나가 순서대로 절대 파일 주소로 들어가고, `@page{size:1080px 1350px;margin:0}`이 있다 |
| 2 | `test_bake_prints_the_pdf_from_the_baked_pngs` (신규, 브라우저 호출을 대체) | `print_pdf`가 `cards.html`이 아니라 PNG 조립 HTML로 불린다. 이미지 수가 다르거나 `/SMask`가 있는 PDF가 나오면 `ValueError`로 멈춘다 |
| 3 | `test_bakes_every_card_and_passes_the_layout_check` (보강, 실제 굽기) | 실제로 구운 PDF에 `/SMask`가 없고 이미지 수가 장수와 같다. **수정 전 코드로 돌리면 실패해야 한다** |

**단계**
1. 테스트 3개를 먼저 쓰고, 수정 전 코드에서 실패하는 것을 확인한다.
2. `render_cards.py`를 고친다. 전체 테스트를 통과시킨다.
3. `pipeline.py --cards intro`로 소개 카드를 다시 굽는다. PNG 5장·`cards.html`·`linkedin.md`가 커밋된 파일과 같은지 대조한다.
4. 새 PDF를 pdf.js로 다시 재서 가장자리 편차가 0인지 확인한다.
5. 문서를 갱신하고 로컬 커밋한다. 개인정보 검사 후 **push 승인을 받는다**(규칙 4).
6. push 뒤 게시 워크플로가 끝나면 게시 주소의 PDF가 저장소 파일과 같은지 확인한다.

**위험**

| 위험 | 대응 |
|---|---|
| 헤드리스 브라우저가 임시 폴더(한글 사용자 경로)의 HTML에서 다른 폴더의 PNG를 못 불러 빈 쪽이 된다 | 이미지 수 검사가 막는다. 실제 굽기 테스트가 로컬·CI에서 확인한다 |
| CI 브라우저의 PNG에 알파 채널이 있어 이미지 마스크(`/SMask`)가 생긴다 | 로컬 PNG는 알파 없는 RGB다(색 형식 2) [확인]. CI에서 다르면 CI 실제 굽기 테스트가 실패해 드러난다 |
| 다시 구운 PNG가 미세하게 달라진다 | 3단계에서 바이트 대조. 다르면 멈추고 보고한다 |

**완료 기준:** 테스트 132개 통과. 소개 카드 PDF에 `/SMask` 0개, 이미지 5개, 가장자리 편차 0. PNG·게시문 변경 없음. 게시 주소 반영 확인.

### 실행 결과 (2026-09-15, 로컬)

**한 일**
1. 테스트 3개를 먼저 썼다. 수정 전 코드에서 3개 모두 실패했다. 실제 굽기 테스트는 7장인데 PDF 이미지가 10개였다(강조 문구용 내부 이미지 포함) [확인].
2. `publish/render_cards.py`
   - `pdf_pages_html(pngs)`를 추가했다.
   - `bake()`는 PNG를 모두 구운 뒤 이 HTML을 임시 폴더에 써서 PDF로 굽는다.
   - 쪽수, 이미지 수, `/SMask`를 검사한다.
3. 전체 테스트 132개 통과(137초).
4. `pipeline.py --cards intro`로 소개 카드를 다시 굽고 로컬 커밋했다(`a5af3a8`).

**실측 [확인]**

| 항목 | 이전 PDF | 새 PDF |
|---|---|---|
| 크기 | 309,834바이트 | 273,914바이트 |
| 쪽 / 이미지 / `/SMask` | 5 / 3 / 11 | 5 / 5 / 0 |
| PDF 제목 | `cards` | `cards` |
| 표지 강조 상자 오른쪽 가장자리 편차(1.37배 / 2.13배 / 3배) | 2.0 / 1.7 / 13.2 | 0.0 / 0.0 / 0.0 |

- PNG 5장은 커밋된 파일과 **바이트 단위로 같다**.
- `cards.html`·`linkedin.md`는 저장소 기준 변경이 없다. 작업 사본의 줄바꿈(CRLF)만 다르다.
- 레이아웃 검사 통과: 가장 좁은 여백 245px, 가장 오른쪽 글자 끝 1020/1032px. 이전 굽기와 같다.
- PDF 메타데이터에 로컬 경로와 이메일이 없다. 커밋 대상 코드 개인정보 검사 0건.

**계획과 달라진 점**

| 계획 | 실제 | 이유 |
|---|---|---|
| 조립 HTML은 `@page`와 `<img>`만 | `<title>cards</title>`을 넣었다. 테스트 1에 확인을 더했다 | 첫 굽기에서 PDF 제목이 임시 파일 이름 `pdf-pages.html`로 기록됐다 [확인]. 이전 PDF와 같은 제목을 유지한다 |

**막혔던 것**
- 앱 안 브라우저가 로컬 파일을 열지 못해, 헤드리스 Edge에서 pdf.js로 렌더링해 쟀다.
- `<head>` 안 스크립트가 `document.body`를 찾지 못해 측정이 멈췄다. 스크립트를 `<body>` 뒤로 옮겨 해결했다.
- 측정 파일은 `_workspace/seam-probe/`(커밋 제외)에 있다.

**남은 것**
- push 승인 → 게시 워크플로 → 게시 주소의 PDF가 저장소 파일과 같은지 확인.
- CI의 실제 굽기 테스트(한글 글꼴 설치 후)는 다음 매일 수집 실행에서 새 PDF 경로로 돈다. CI 브라우저에서도 `/SMask`가 없는지 그때 확인한다.
- 확인이 끝나면 사용자가 PDF를 게시한다.
